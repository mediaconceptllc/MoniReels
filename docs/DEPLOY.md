# Байршуулах

Гурван зүйл: Railway дээр **хоёр сервис** (API ба worker), Vercel дээр вэб,
Cloudflare дээр R2 сан.

Хоёр Railway сервис нь **нэг Dockerfile-аас, нэг commit-оос** build хийгдэнэ,
эхлэх команд нь өөр. Image нь харин ижил БИШ байж болно: worker сервист
`INSTALL_DUB=1` тавьбал түүний image-д torch, Demucs ба загварын жин
нэмэгдэнэ (§4 «Цэвэр дубляж»), API-гийнх нимгэн хэвээр. Хоёр тусдаа
Dockerfile хөтлөх шаардлагагүй — тэгвэл кодын хувилбар нь зөрөх эрсдэлтэй.

## 1. Cloudflare R2

1. R2 → **Create bucket** → нэр нь `monireels`.
2. **Manage R2 API Tokens** → *Object Read & Write*, зөвхөн тэр сан руу.
3. Account ID, Access Key ID, Secret Access Key гурвыг тэмдэглэ.

**`R2_ACCOUNT_ID` нь токены утга БИШ.** Токен үүсгэсний дараа гарах
хуудсанд дөрвөн зүйл зэрэг харагдана — Token value (`cfat_…`), Access Key
ID, Secret Access Key, ба S3 endpoint. Account ID нь **зөвхөн endpoint-ийн
дотор** байдаг:

```
https://0123456789abcdef0123456789abcdef.r2.cloudflarestorage.com
        └──────── R2_ACCOUNT_ID (16 хос hex) ───────┘
```

Endpoint-ыг бүтнээр нь тавьсан ч ажиллана (`config.r2_account` таслаж
авна). Токены утгыг тавьбал `r2_config_error` эхний хүсэлт дээр
татгалзана — тэр утга ХЭЗЭЭ Ч алдааны мессеж, лог руу орохгүй (токеноос
Secret Access Key гардаг тул лог руу орсон токен нь алдагдсан нууц).

**CORS ЗААВАЛ.** Хөтөч шууд PUT хийдэг тул CORS-гүй бол хуулалт preflight
дээр л унана — алдаа нь сүлжээний алдаа мэт харагдана.

```json
[
  {
    "AllowedOrigins": ["https://<таны-vercel-домэйн>", "http://localhost:3000"],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["content-type"],
    "ExposeHeaders": ["etag"],
    "MaxAgeSeconds": 3600
  }
]
```

Сан **хаалттай** үлдэнэ (public access идэвхжүүлэхгүй): бүх хандалт signed
URL-аар явна.

**Том файл хэсэгчилж хуулагдана (multipart, UP-1).** Нэг PUT ≈5 GiB-ээс том
объект хүлээж авдаггүй тул 64 MiB-ээс том видеог хөтөч 16 MiB-ийн хэсгүүдээр
(20 GiB файл = 1 280 хэсэг) хэсэг тутмын presigned URL руу шууд илгээнэ.
Тасарсан хэсэг дангаараа дахин илгээгдэнэ, хуудас дахин ачаалсны дараа ижил
файлыг сонговол хадгалагдсан хэсгүүд дахин илгээгдэхгүй. **CORS-д өөрчлөлт
шаардлагагүй**: хэсгийн хүсэлт нь дээрх дүрмийн `PUT` бөгөөд `Content-Type`
толгойгүй. Сервер объектыг R2-ийн өөрийн хэсгийн жагсаалтаас угсардаг тул
хөтөч `ETag` уншихгүй.

Дуусаагүй хэсгүүд **төлбөртэй** бөгөөд объектын жагсаалтад харагддаггүй.
Цуцлах, төсөл устгах, дахин хуулах үед тэр төслийн дутуу хуулалт шууд
цуцлагдана. Хөтөч хаагдаж орхигдсон хуулалтыг worker-ийн housekeeping
`R2_MPU_ABORT_H` (анхдагч 24 цаг) өнгөрсний дараа цуцална. Маш удаан холболтоор
20 GiB-ийг 24 цагаас удаан хуулах бол энэ утгыг өсгөнө (дахин эхлүүлэх нь 24
цагийн дотор л боломжтой). Хүсвэл R2 bucket дээр «abort incomplete multipart
uploads» lifecycle дүрэм нэмж болно — заавал биш, нөөц хамгаалалт.

## 2. Railway — Postgres

**New → Database → PostgreSQL.** `DATABASE_URL`-ыг сервис хоёуланд нь өг.

Миграц нь **API сервисийн эхлэлд** ажиллана (`app/migrate.py`, Postgres
advisory lock-оор хамгаалагдсан). Worker миграц хийхгүй — нэг бичигч л
хангалттай, ба хоёулаа хийвэл deploy бүрд уралдана. Railway хоёр сервисийг
зэрэг асаадаг тул worker эхний ажлаа авахаасаа өмнө DB-г кодын migration
head-д хүрэхийг **хүлээнэ** (лог: «Waiting for the API to migrate the database
to …», минут тутам нэг мөр). DB кодоос шинэ (rollback) бол анхааруулга бичээд
шууд ажиллана — миграцууд зөвхөн нэмдэг тул хуучин код шинэ схем дээр
ажиллана.

API ч мөн адил (OPS-2):

- **DB кодоос шинэ** (өмнөх хувилбар руу rollback хийсэн) бол API миграц
  хийхгүй, анхааруулга бичээд асна: «The database is at …, newer than this
  code's …: not migrating (a rollback?)». Өмнө нь `alembic upgrade head` нь
  мэдэхгүй revision дээр «Can't locate revision» гэж унаж, API огт асдаггүй
  байв — ажилладаг хувилбар хамгийн их хэрэгтэй яг тэр мөчид.
- **DB түр хүрэхгүй** байвал API `DB_STARTUP_WAIT_S` (60) секунд дахин
  оролдоно (1, 2, 4, 8, 10 … секундын зайтай, оролдлого бүрийг логт
  нэрлэнэ). Хугацаа дуусвал шалтгаанаа нэрлээд **гарна** — ингэснээр
  Railway-ийн restart ба «deploy унасан» дохио хоёулаа ажиллана. Өмнө нь
  эхний татгалзсан холболт л процессыг унагаадаг байсан тул DB deploy-той
  зэрэг дахин асахад restart-ын цөөн оролдлого хэдхэн секундэд дуусдаг
  байв. Холболтын нэг оролдлого `DB_CONNECT_TIMEOUT_S` (10) секундээр
  хязгаарлагдана — эс бөгөөс пакет хаядаг хост TCP-ийн ~2 минут барина.
  `DB_STARTUP_WAIT_S`-ийг API-ийн healthcheck timeout-оос (120) бага байлга.

### Миграцын дүрэм: expand / contract

Rollback аюулгүй байх цорын ганц нөхцөл нь: **өмнөх хувилбарын код шинэ
схем дээр ажиллах ёстой.** Тиймээс миграц зөвхөн НЭМНЭ:

- шинэ хүснэгт, шинэ индекс — болно;
- шинэ багана — `nullable=True`, эсвэл `server_default`-той `NOT NULL`
  (хуучин код тэр баганыг мэдэхгүй тул INSERT-дээ бөглөхгүй);
- багана/хүснэгт **устгах, нэр солих, төрөл солих, `NOT NULL` болгох,
  түүхий `op.execute`** — ХОРИОТОЙ, хэрэв өмнөх хувилбар түүнийг ашигладаг
  бол.

Ийм өөрчлөлт хэрэгтэй бол хоёр release болгож хуваа: эхлээд **expand**
(шинийг нэмж, код шинийг ашиглана, хуучин нь хэвээр), дараагийн release-д
**contract** (код хуучныг ашиглахаа больсны дараа устгана). Contract
миграцад модулийн түвшинд `CONTRACT = "<яагаад аюулгүй>"` тавина.
`tests/test_rollback.py::test_every_migration_only_adds` бүх миграцын
`upgrade()`-ийг уншиж энэ дүрмийг барина — жагсаалт биш, дүрэм.

Одоогийн 0001–0004 бүгд зөвхөн нэмдэг (шинэ хүснэгт, nullable багана).

### Кодыг буцаах (rollback)

Railway → сервис → **Deployments** → өмнөх deploy-ийн «⋯» → **Rollback**.
Rollback нь тухайн deploy-ийн image ба хувьсагчдыг сэргээнэ
([Roll Back a Bad Deploy](https://docs.railway.com/guides/roll-back-bad-deploy),
[Deployment Actions](https://docs.railway.com/deployments/deployment-actions#rollback)).
**API ба worker хоёуланг** буцаа — нэг Dockerfile, нэг commit тул хоёулаа нэг commit-д байх ёстой.

- **Аюулгүй:** миграц нь дээрх дүрмийг дагасан бол. API ба worker хоёулаа
  шинэ схем дээр асна (логт «newer than this code» анхааруулга).
- **Аюулгүй БИШ:** contract миграц (устгалт) орсон release-ээс өмнөх
  хувилбар руу буцах. Тэр үед схемийг буцаах нь `alembic downgrade`
  (өгөгдөл устах эрсдэлтэй) эсвэл доорх нөөцөөс сэргээх — хоёулаа
  гараар, эхлээд нөөц ав.
- **Өгөгдөл:** шинэ кодын бичсэн мөрийг хуучин код таних ёстой. Жишээ нь
  #64-өөс хойш ажлын `lane` нь `stt`/`llm` — worker ажлыг kind-аар нь
  авдаг тул хуучин нэр ч, шинэ нэр ч асуудалгүй.

### Нөөц ба сэргээлт

Railway-ийн Postgres нь volume дээр ажилладаг. Нөөцийн гурван давхарга бий
([Back Up and Restore Postgres](https://docs.railway.com/guides/postgres-backups-restores),
[Backups](https://docs.railway.com/volumes/backups),
[Point-in-Time Recovery](https://docs.railway.com/volumes/point-in-time-recovery)):

1. **Хуваарьт volume backup** — Postgres сервис → **Backups** таб →
   schedule. Daily (6 хоног хадгална), Weekly (27 хоног), Monthly (89
   хоног); хэд хэдийг зэрэг сонгож болно. **Daily + Weekly**-г асаа. Гараар
   ч backup авч болно (volume-ийн хэмжээний 50% хүртэл). Volume-ийг wipe
   хийвэл бүх backup устана.
2. **Point-in-time recovery (PITR)** — WAL-ийг bucket руу архивлаж, ойролцоогоор
   4 долоо хоногийн дотор дурын цэг рүү сэргээнэ (Railway-ийн storage bucket
   ашиглана). Хэрэгтэй бол асаа.
3. **`pg_dump`** — Railway-ээс гадна хадгалах логик хуулбар (доорх
   туршилтад хэрэглэнэ).

**Бодит сэргээлт (volume backup-аас):** Backups таб → огноогоор нь олж
**Restore**. Railway өөрчлөлтийг шууд хэрэглэхгүй, **staged change**
болгоно: backup-ийн огноогоор нэрлэсэн шинэ volume ижил зам дээр холбогдож,
хуучин volume салгагдана, гэхдээ **устахгүй** (буцах зам үлдэнэ). Шалгаад
**Deploy** дарвал сервис сэргээсэн өгөгдөл дээр дахин асна. Сэргээлт зөвхөн
ижил project + environment-д. Сэргээсний дараа DB кодоос хуучин байж болно
— API асахдаа өөрөө миграц хийнэ («behind»).

**Сэргээлтийн туршилт — ХЭРЭГЛЭГЧИЙН АЛХАМ, ХАРААХАН ХИЙГДЭЭГҮЙ.** Хэзээ ч
сэргээж үзээгүй нөөц бол баталгаагүй нөөц. Production-ийн volume-ийг
дарахгүйн тулд туршилтыг **тусдаа** Postgres дээр хий:

1. Production Postgres-ийн public URL-ээр `pg_dump -Fc -f monireels.dump "$URL"`.
2. Түр Postgres үүсгэ (тусдаа project эсвэл environment, эсвэл локал).
3. `pg_restore --no-owner -d "$TEMP_URL" monireels.dump`.
4. Шалга: `SELECT version_num FROM alembic_version;` нь production-тай
   ижил, `users`, `projects`, `jobs`, `usage_events`-ийн мөрийн тоо
   ойролцоо.
5. Түр DB-г устга, хийсэн огноо ба зарцуулсан хугацааг энд бич:

| Огноо | Хэн | Нөөц | Сэргээх хугацаа | Үр дүн |
|---|---|---|---|---|
| — | — | — | — | хийгдээгүй |

## 3. Railway — API сервис

Тохиргоо бүгд **Railway-ийн dashboard дээр** (сервис → Settings). Репод
`railway.json` байхгүй — доорх «Тохиргоо хаана байдаг» хэсгийг үз.

- **Root directory:** `backend`
- **Builder:** Dockerfile
- **Start command:** `python -m app.main`
- **Healthcheck path:** `/health`, timeout `120`
- **Restart policy:** **Always** (paid plan; Free/trial дээр On failure, 10).
  Одоо dashboard дээр «On failure, 3» байгаа бол соль: DB 3 минутаас удаан
  унтарвал API гурван оролдлогоо (тус бүр `DB_STARTUP_WAIT_S`) дуусгаад
  бүрмөсөн зогсох байлаа
  ([Restart Policy](https://docs.railway.com/deployments/restart-policy)).
- **Draining seconds:** `30` — ажиллаж буй хүсэлт дуусах зай

Хувьсагчид:

```
DATABASE_URL=${{Postgres.DATABASE_URL}}
JWT_SECRET=<python -c "import secrets; print(secrets.token_urlsafe(48))">
SETTINGS_ENCRYPTION_KEY=<python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())">
BOOTSTRAP_ADMIN_USERNAME=admin
BOOTSTRAP_ADMIN_PASSWORD=<хүчтэй нууц үг>
CORS_ORIGINS=https://<таны-vercel-домэйн>
R2_ACCOUNT_ID=...
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
R2_BUCKET=monireels
OPENROUTER_API_KEY=...
OPENROUTER_MODEL=anthropic/claude-sonnet-4.5
DUUDLAGA_API_KEY=...
DUUDLAGA_BASE_URL=https://api.duudlaga.dev/v1
ELEVENLABS_API_KEY=...
```

`OPENROUTER_API_KEY`, `DUUDLAGA_API_KEY`, `ELEVENLABS_API_KEY`,
`OPENROUTER_MODEL` ба монгол дууны загвар, хоолойг (`ELEVENLABS_TTS_MODEL`,
`ELEVENLABS_TTS_VOICE_ID`) **Тохиргоо хуудсанаас** (админ, `/admin`) ч
оруулж болно — хоолойг тэнд данс дахь жагсаалтаас нэрээр нь сонгоно. Хуудсан дээрх утга орчны хувьсагчийг дарах ба **дараагийн
ажлаас эхлэн** хүчинтэй: API ба worker хоёулаа тэр мөрийг ажил тутам
уншдаг тул redeploy ч, restart ч шаардахгүй. Талбарыг хоосон болгож
хадгалбал мөр устаж, орчны хувьсагч руу буцна — эс бөгөөс нэг андуурч
бичсэн түлхүүр мөнхөд хоцорно.

Түлхүүр хаана байхаас үл хамааран **буцаж уншигдахгүй**: `GET
/admin/settings` нь эх сурвалж ба сүүлийн 4 тэмдэгтийг л өгнө.

**Хуудсаар оруулсан түлхүүрийг өгөгдлийн санд шифрлэнэ** —
`SETTINGS_ENCRYPTION_KEY` (Fernet түлхүүр) тавьсан үед. Үгүй бол түлхүүр
`settings` хүснэгтэд цэвэр текстээр хадгалагдах ба DB-ийн dump, нөөц
хуулбартай хэн ч бүх төлбөртэй дансыг авна; Тохиргоо хуудас үүнийг
сэрэмжлүүлж хувьсагчийн нэрийг хэлнэ.

- **API ба worker ХОЁУЛАНД ижил утгаар** тавина: worker ажил тутам түлхүүрийг
  тайлдаг.
- Тавьсны дараах эхний асалтаар API өмнө нь хадгалсан түлхүүрүүдийг өөрөө
  шифрлэнэ (логт «Sealed N stored provider key(s)»).
- **Солих:** шинэ түлхүүрийг ЭХЭНД нь, хуучныг ард нь таслалаар —
  `SETTINGS_ENCRYPTION_KEY=<шинэ>,<хуучин>`. API нэг асмагц бүгдийг шинээр
  шифрлэнэ, дараа нь хуучныг хасна.
- **Түлхүүрээ алдвал** хадгалсан API түлхүүрүүдийг тайлах боломжгүй:
  төлбөртэй ажил «SETTINGS_ENCRYPTION_KEY» гэсэн шалтгаантай зогсоно,
  Тохиргоо хуудас аль түлхүүр уншигдахгүйг нэрлэнэ. Засвар нь түлхүүрүүдийг
  хуудсаар дахин оруулах.
- Буруу хэлбэрийн утга тавибал API **асахгүй**, шалтгааныг логт нэрлэнэ
  (утгыг нь хэвлэхгүй).
- Хэн хэзээ аль түлхүүрийг сольсон нь `audit_log`-д бичигдэнэ (утга нь биш).

`BOOTSTRAP_ADMIN_*` нь **users хүснэгт хоосон байхад л** ажиллана. Тиймээс
дараа нь солиход байгаа бүртгэл чимээгүй дахин тохируулагдахгүй. Эхний
удаа нэвтэрсний дараа нууц үгээ солино — тэр үед өмнөх бүх токен нэн
даруй хүчингүй болно.

`CORS_ORIGINS` **хоосон бол хөтөч бүх хүсэлтийг хаана.** `*` тавибал API
**асахгүй** (логт шалтгааныг нэрлэнэ): credentials-тай үед Starlette `*`-ыг
асуусан ямар ч origin-ыг буцааж тусгадаг тул бүх сайтад нээлттэй болно.

`JWT_SECRET` **32 байтаас богино (эсвэл хоосон) бол API асахгүй.** Дээрх
`token_urlsafe(48)` нь 64 тэмдэгт гаргана. Солиход бүх хэрэглэгч нэг удаа
гарна.

## 4. Railway — Worker сервис

Ижил репо, ижил Dockerfile, зөвхөн:

- **Start command:** `python -m app.worker`
- **Healthcheck:** ТАВИХГҮЙ (worker HTTP сонсдоггүй)
- **Restart policy:** Always
- **Replicas:** 1
- **Draining seconds:** `600` — **заавал** (доор). Анхдагч нь 0.

Хувьсагчид нь API-тай ижил (`CORS_ORIGINS`-оос бусад — `SETTINGS_ENCRYPTION_KEY`
ЗААВАЛ ижил утгаар). Нэмж:

```
WORK_FREE_MIN_MB=2048
```

`WORKER_LANES` хоосон бол анхдагч `heavy=1,stt=1,llm=2` ажиллана (доорх
«Эгнээ»). Өмнө нь энд `WORKER_CONCURRENCY=2` бичигдсэн байсан. **Dashboard
дээр тэр хувьсагч байгаа бол устга**: одоо тэр нь заавал биш нийт таазны
утгатай. 2 гэж үлдвэл render ба transcribe зэрэг явж байхад санал
(suggest) хүлээсээр байна. Worker асахдаа лог дээр анхааруулга бичнэ.

**Worker-гүй бол ямар ч ажил ажиллахгүй** — job нь `queued`-д мөнхөд
үлдэнэ. Вэб дээрх «Ажлын дараалалд N ажил хүлээж байгаа ч ажиллаж буй
worker алга» гэсэн сэрэмжлүүлэг яг үүнийг барина.

### Image root биш хэрэглэгчээр ажиллана

Image `app` (uid 10001) хэрэглэгчээр ажиллана (OPS-7): ffmpeg гаднын хүний
хуулсан медиаг уншдаг тул түүний алдаа ямар нэг эрхгүй бүртгэлд л буух
ёстой. Хоёр нөхцөл:

- **`WORK_DIR` нь `/tmp` дотор байна** (анхдагч `/tmp/monireels`). Өөр газар
  заасан ба тэр нь энэ хэрэглэгчид бичигдэхгүй бол `/tmp/monireels` руу
  шилжиж, логт «WORK_DIR … is not writable … using /tmp/monireels instead»
  гэж нэг удаа бичнэ — volume байхгүй тул scratch хаана ч байсан контейнерийн
  ижил диск. Тэр ч бичигдэхгүй бол нэрлэсэн алдаагаар зогсоно.
- **Volume холбохгүй.** Railway-ийн volume root-ийн эзэмшилд байдаг. Хэзээ
  нэгэн цагт хэрэгтэй болбол тухайн сервис дээр `RAILWAY_RUN_UID=0` тавьж
  root руу буцна (Railway-ийн баримт бичигт заасан зам).

### Worker гацвал өөрөө дахин асна

Railway worker-ийг зөвхөн процесс нь гарвал дахин асаадаг. Healthcheck нь
зөвхөн deploy-д хэрэглэгддэг ба зөвхөн порттой сервист ажилладаг. Docker-ийн
`HEALTHCHECK`-ийг Railway огт уншдаггүй. Тиймээс worker өөрийн давталтыг
хянадаг (`LOOP_STALL_EXIT_SEC`, 15 минут). Давталт 15 минут эргэхгүй бол
(жишээ нь тасарсан TCP холболт дээр гацсан claim) worker лог дээр
`The worker loop has not turned` гэж бичээд гарна. Restart policy `Always`
түүнийг дахин асаана, гацсан ажлыг reaper дараалалд буцаана.

### Зогсолтын хүлээлт (deploy ажлыг алахгүйн тулд)

Railway нь шинэ deploy идэвхжмэгц хуучинд `SIGTERM` илгээж, тодорхой
хугацааны дараа `SIGKILL` хийнэ. **Анхдагч нь 0 секунд** —
ХЭМЖИГДСЭН: 4–5 минутын speech-to-text дуудлагын 58 дахь секундэд deploy
буусан ба контейнер 10 секундын дараа алга болсон. `transcribe`, `suggest`
хоёр нь оролдлого тутам төлбөртэй ба ДАХИН АЖИЛЛАДАГГҮЙ, тиймээс тэр нь
дэмий зарцуулсан мөнгө.

Хоёр тоо хамтдаа ажиллана:

| Хаана | Юу | Утга |
|---|---|---|
| Railway → worker → Settings → Deploy | Draining seconds | `600` — платформ хэзээ алах вэ |
| `backend/app/config.py` | `WORKER_DRAINING_S` | `600` — дээрхийн хуулбар, тестэд |
| `backend/app/config.py` | `worker_shutdown_grace_s` | `580` — worker хэдийг хүлээх вэ |

Аппын хүлээлт нь платформынхаас **заавал бага** байх ёстой: эс бөгөөс
worker хүлээж байхдаа алагдаж, юу ч бүртгэгдэхгүй. `test_worker_shutdown`
тэр харьцааг тулгана. Платформын утга dashboard дээр байдаг тул тест
`WORKER_DRAINING_S`-ийг уншина — **нэгийг нь солиход нөгөөг нь хамт сольно.**

Хугацаа дуусахад дуусаагүй ажил **НЭРЛЭГДЭНЭ**: дахин ажиллаж болох
төрлүүд дараалалд буцна, төлбөртэй нь «deploy зогсоосон» гэсэн шалтгаантай
`failed` болно (дахин оролдох нь хоёр дахь төлбөр). Хоосон worker дээр энэ
нь юу ч зардаггүй — ажилгүй бол хоёр секундэд гарна.

### Тохиргоо хаана байдаг

Сервисийн тохиргоо (start command, healthcheck, restart, replicas, draining)
**зөвхөн Railway-ийн dashboard дээр**. Репод `backend/railway.json`,
`backend/railway.worker.json` байсан ч энэ төслийн deploy-ууд тэднийг
**уншаагүй**: Railway-ийн deploy-ийн бүртгэлд `configFile: null`, файлын
manifest хоосон; worker-ийн тохиргоонд `drainingSeconds` огт байгаагүй
(анхдагч 0 — дээрх 10 секунд яг тэр); API-ийн healthcheck файлд 60,
dashboard дээр 120 байв. Railway config-as-code-ийг
**2026-12-01**-нээс бүрмөсөн уншихаа больсон тул файлуудыг устгаж, утгыг
dashboard дээр тавьсан (2026-10-19, OPS-8). Infrastructure as Code
(`.railway/railway.ts`) руу шилжих бол Railway CLI-ийн `railway config
pull` нь одоогийн dashboard-ийг файл болгоно — тэр үед энэ хэсгийг шинэчил.

### Эгнээ (lane) — worker бүр өөрийн ажлыг тоолно

Нэг worker нэг дор хэдэн ажил ажиллуулахыг эгнээгээр хязгаарлана. Эгнээ бүр
нэг нөөцийг илэрхийлнэ:

| Эгнээ | Ажил | Анхдагч | Нөөц |
|---|---|---:|---|
| `heavy` | import, export | 1 | тухайн хайрцгийн CPU/RAM/диск |
| `stt` | transcribe | 1 | яриа таних провайдер (4 хүсэлт зэрэг, 6 GB scratch) |
| `llm` | suggest, translate | 2 | OpenRouter |

Хязгаарыг **worker бүр өөрөө** тоолно. Өмнө нь энэ тоо бүх систем даяар нэг
байсан (ARCH-2). Тиймээс нэг хэрэглэгчийн 8 минутын transcribe нөгөө
хэрэглэгчийн санал авах хүсэлтийг хүлээлгэдэг байв. Мөн хоёр дахь worker нэг
нь render хийж байх хооронд сул зогсож, дараалалд байгаа хоёр дахь export-ыг
авдаггүй байлаа.

Replica нэмбэл эгнээ бүр түүнийг дагаж өснө: 2 worker = 2 render, 2
transcribe. Иймээс provider-ийн консол дээрх зэрэгцээ хүсэлтийн хязгаарыг
`replica × stt × DUUDLAGA_CONCURRENCY`-аар тооцоол.

**Ирээдүйд I/O ба render-ийг тусад нь ажиллуулах** (жишээ нь heavy эгнээний
p95 хүлээлт хоёр долоо хоног 15 минутаас их байвал): ижил Dockerfile-аас хоёр worker сервис үүсгэж, dashboard дээр
`WORKER_LANES`-ийг өөр өөрөөр тавина.

- render pool: `WORKER_LANES=heavy=1`. Том CPU/RAM/диск, dub image.
- I/O pool: `WORKER_LANES=stt=2,llm=4`. Жижиг хэмжээ.

Жагсаалтад ороогүй эгнээг тухайн worker огт ажиллуулахгүй. Буруу бичвэл
(`hevy=1`) worker асахгүй — эгнээ чимээгүй унтрахаас асахгүй байх нь дээр.

Эгнээ бүрийг ядаж нэг worker ажиллуулж байх ёстой. Эс бөгөөс тэр эгнээний
ажил дараалалд мөнхөд үлдэнэ. Worker бүр өөрийн мөрийг `worker_heartbeats`
хүснэгтэд минут тутам бичдэг (эгнээ, commit, Demucs, диск) тул Админ →
Ажлууд хуудас эгнээ тус бүрээр «Гүйцэтгэх worker алга» гэж, хүлээж буй ажил
байвал анхааруулгаар нэрлэнэ — нэг pool зогсож нөгөө нь амьд үед ч. Цэвэр
унтарсан worker мөрөө тэр дор нь устгана, гэнэт үхсэнийх 3 минутын дараа
«Зогссон» болж, нэг цагийн дараа цэвэрлэгдэнэ.

### Цэвэр дубляж — эх яриаг арилгах (сонголт)

Монгол дуу оруулахад эх яриаг намсгахын оронд бүрэн хасна: Demucs нь
экспортлох хэсэг бүрийн яриаг хөгжим, орчны чимээнээс салгаж хаяна.
Төсөл тутамд Экспортын тохиргоо → «Эх яриа: Арилгах».

**Асаах:** Worker сервисийн Variables-д

```
INSTALL_DUB=1
```

тавиад дахин deploy хийнэ. **API сервист ТАВИХГҮЙ.** Railway нь сервисийн
хувьсагчийг Dockerfile-ийн build-д зөвхөн `ARG`-аар нэрлэгдсэн үед
дамжуулдаг — Dockerfile-д `ARG INSTALL_DUB` бий, тиймээс хоёр сервис нэг
Dockerfile-аас өөр image гаргана. Build нь torch (CPU), Demucs ба загварын
жинг (`/opt/models`) image-д шингээнэ — экспортын дундуур юу ч татахгүй.

- **Image томорно.** CPU torch дангаараа ~800 МБ (`requirements.txt`-ийн
  тайлбар). CI-ийн «Worker image with the clean dub» алхам жинхэнэ хэмжээг
  логдоо бичнэ.
- **Төлбөргүй, харин CPU хугацаа.** Зөвхөн экспортлох хэсгүүдийг салгана,
  бүтэн видеог биш; хэсэг бүрийг нэг л удаа — R2-д
  `audio/{project}/bed-….flac` болж хадгалагдана, дахин экспорт CPU дахин
  зарцуулахгүй. Thread-ийн тоо `config.heavy_threads`-аар контейнерийн
  quota-д багтана.
- **Санах ой хэмжигдээгүй.** Эхний цэвэр дубляжийн үед Railway-гийн
  Metrics-ээс worker-ийн RAM-ыг хар; дутвал worker-ийн нөөцийг өсгө.
- **Шалгах:** worker асаад нэг минутын дотор Админ → «Юу юуг ажиллуулж
  байна» дээр «Эх яриа арилгах» мөр «Ажиллаж байна» болно (worker
  чадвараа ДБ-д өөрөө бичдэг — API image-д Demucs байхгүй тул тэр өөрөө
  шалгаж чадахгүй).
- **Асаагаагүй бол** «Арилгах»-тай экспорт ЭХЛЭХЭЭС ӨМНӨ шалтгаантайгаа
  зогсоно — хоолой төлөгдөхгүй. «Намсгах» ямар ч worker дээр ажиллана.

`INSTALL_DUB` нь яриа танихыг ӨӨРЧЛӨХГҮЙ: silero-vad ордоггүй, ба
`ENABLE_SEPARATION` асаалттай байсан ч VAD-гүй үед STT салгалт хийхгүй
(салгасан хоолойг зөвхөн VAD уншдаг).

### Хэрэв нарийвчлал сайжруулах бол (сонголт)

VAD ба Demucs-ыг асаах:

1. `Dockerfile` нь одоогоор үүнийг суулгадаггүй. Нөхцөлгүй
   `RUN pip install -r requirements-ml.txt` НЭМЭХГҮЙ: Dockerfile нь API ба
   worker хоёрт нэг тул torch API image-д ч орно. `INSTALL_DUB`-ийн хажууд
   ижил хэлбэрийн build ARG нэмж зөвхөн worker сервист асаана:

   ```dockerfile
   ARG INSTALL_ML=0
   COPY requirements-ml.txt ./
   RUN if [ "$INSTALL_ML" = "1" ]; then pip install --no-cache-dir -r requirements-ml.txt; fi
   ```

   `requirements-ml.txt` нь `requirements-dub.txt`-ийг (torch, Demucs) агуулдаг
   тул нэмэгдэх нь silero-vad ба soundfile.
2. `ENABLE_SEPARATION=true`

**Зөвхөн worker сервист.** torch нь контейнерийн cgroup CPU хязгаарыг
УНШИХГҮЙ — thread pool-оо хостын цөмөөр гаргаж quota давна, цөм нь бүх
контейнерийг throttle хийнэ. Тэр контейнер HTTP ч хариулдаг бол healthcheck
хожимдож, Railway сервисийг ажлын дундуур ДАХИН АСААНА.
`config.heavy_threads` жинхэнэ quota-г уншиж хязгаарыг тавьдаг ч аюулгүй
зохион байгуулалт нь тусдаа сервис хэвээр.

## 5. Vercel

- **Root directory:** `frontend`
- **Framework:** Next.js (автоматаар танина)

```
NEXT_PUBLIC_API_URL=https://<railway-api-домэйн>
```

Энэ нь **build-д шингэдэг** тул солиход дахин deploy шаардана. Тэр нь зөв:

тохиргоо биш.

**Одоогийн production утга репод байна:** `frontend/vercel.json`-ийн

commit хийнэ. `build.env` нь Vercel-ийн хуучирсан (legacy) талбар тул

Deploy хийсний дараа Vercel-ийн домэйныг Railway-гийн `CORS_ORIGINS` руу

production домэйныг л нэмэхэд хангалттай.

## Шалгах жагсаалт

```bash
curl https://<api>/health
# {"status":"ok","ffmpeg":true,"storage":true,...}
```

- `ffmpeg: false` → image буруу баригдсан
- `storage: false` → `R2_*` дутуу. `GET /admin/providers` аль хувьсагч
  буруу болохыг нэрлэнэ; хуулалт 503 буцаавал шалтгаан нь хариунд гарна
- Нэвтэрч чадахгүй → `JWT_SECRET` тавигдаагүй, эсвэл bootstrap ажиллаагүй
  (users хүснэгт аль хэдийн хоосон биш)
- Хуулалт 403 → R2-гийн CORS
- Job мөнхөд `queued` → worker сервис ажиллаагүй
- Transcribe «кредит дууссан» гэж унасан → `GET /admin/providers`
- «Серверт алдаа гарлаа. Лавлах дугаар: …» → Railway-ийн лог дээр
  `@request_id:<дугаар>` гэж хайна (доор)

### Лог ба алдааны тайлан

Лог мөр бүр нэг JSON объект (`LOG_FORMAT=json`, анхдагч): `level`,
`message`, мөн хамаарах **`request_id`** (API) эсвэл **`job_id`** /
`job_kind` (worker). Railway мөрийг `level`-ээр нь ангилж, талбар бүрээр
хайлгана — `@request_id:…`, `@job_id:…`. Хүсэлт бүрийн `X-Request-ID`
толгойд ч ижил дугаар буцна; 500 хариу түүнийг текстэндээ нэрлэнэ.

**Алдааны тайлан (сонголт):** sentry.io дээр төсөл үүсгээд DSN-ийг
**API ба worker хоёуланд** `SENTRY_DSN` болгож тавина. Шийдэгдээгүй алдаа ба
ERROR түвшний лог мөр бүр request/job ID-тайгаа ирнэ. Хүсэлтийн бие, cookie,
`Authorization` толгой **хэзээ ч** илгээгдэхгүй. Тавиагүй бол юу ч ачаалагдахгүй.

**Админы үйлдлийн бүртгэл:** `/admin/...` доорх өөрчлөлт бүр болон нууц үг
солих нь `audit_log` хүснэгтэд нэг мөр үлдээнэ: хэн, хаанаас, юу, ямар
статустай — хүсэлтийн бие хэзээ ч биш. `AUDIT_KEEP_DAYS` (365) хоногоос хуучныг
worker цэвэрлэнэ.

**Өгөгдлийн сангийн хязгаар:** апп-ын холболт бүр `statement_timeout` 60с,
`lock_timeout` 15с, `idle_in_transaction_session_timeout` 5 мин-тэй эхэлнэ
(`DB_*_TIMEOUT_MS`, `0` = хязгааргүй). Миграц өөрийн холболтоор явах тул
хамаарахгүй. Өөр instance миграцын түгжээг `MIGRATION_LOCK_WAIT_S` (600)-аас
удаан барьвал API шалтгаанаа нэрлээд асахаас татгалзана — өмнө нь мөнхөд хүлээдэг байв.
DB-д огт хүрэхгүй бол `DB_STARTUP_WAIT_S` (60) секундын дараа шалтгаанаа нэрлээд гарна
(дээрх «2. Railway — Postgres»).

### Хэрэглэгч тутмын хязгаар (энэ системийн дотор)

Провайдерын консолын хязгаар бүх данс нийлээд хамгаалдаг; энэ нь НЭГ
хэрэглэгчийн бүртгэлийг хязгаарлана (`app/quotas.py`). Дараалал систем
даяар нэг render, нэг төлбөртэй дуудлагатай тул нэг бүртгэл — эсвэл
хулгайлагдсан нууц үг — бусдыг бүгдийг хүлээлгэж, хязгааргүй төлбөр гаргаж
чадах байв. Анхдагч утга нь энгийн ажилд хүрэхгүй; админ хамаарахгүй;
`0` нь тухайн хязгаарыг унтраана.

| Хувьсагч | Анхдагч | Юуг хязгаарлана |
|---|---|---|
| `QUOTA_ACTIVE_JOBS` | 10 | Дараалалд + ажиллаж буй ажил (импорт тоологдохгүй) |
| `QUOTA_ACTIVE_PAID_JOBS` | 3 | Тэдгээрээс төлбөртэй нь (яриа таних, санал, орчуулга) |
| `QUOTA_PROJECTS_PER_HOUR` | 30 | Цагт шинэ төсөл |
| `QUOTA_PROJECTS_TOTAL` | 500 | Нийт төсөл |
| `QUOTA_MONTHLY_USD` | (унтраастай) | Энэ сарын **мэдэгдэж буй** зардал (UTC сар, зарлагын бүртгэлээс) |

Сарын хязгаарт хүрвэл дараагийн төлбөртэй ажил ба монгол дуутай экспорт
`429`-өөр татгалзагдана. Үнэ нь тодорхойгүй хүсэлт (яриа таних/дуу
оруулалтын үнийг `*_USD_PER_*`-аар тохируулаагүй) энэ дүнд **орохгүй** —
тэгээр тооцохгүй, татгалзах мессеж тэдний тоог нэрлэнэ. Хязгаар яриа
танихыг ч харах ёстой бол тэр үнийг тохируулна уу.

Хуулалт дуусахад (`upload-complete`) R2 дахь файлын хэмжээг зарласан
хэмжээ ба дээд хэмжээтэй (20 GB) тулгана; зөрвөл файл устгагдаж хуулалт
татгалзагдана.

### Төлбөрийн хязгаар ЗААВАЛ тавь

duudlaga.dev-ийн шинэ түлхүүр **хязгааргүй** эхэлдэг. Консол дээрээс
дараах гурвыг тавь:

| Хязгаар | Яагаад |
|---|---|
| Өдрийн зарлага | Гацсан давталт, эсвэл алдаагаар олон удаа эхлүүлсэн ажил нэг шөнийн дотор данс хоослох боломжтой. |
| Зэрэгцээ хүсэлт | `WORKER_LANES` (`stt`) нь **ажлыг** хязгаарладаг, хүсэлтийг БИШ. Нэг transcribe ажил аудионы хэсэг тутамд нэг хүсэлт явуулна — 40 минутын видео 40+ хүсэлт болно. |
| Хүсэлтийн хурд | Дээрхтэй ижил шалтгаан. |

Хязгаарт хүрвэл API `429`-ийг `Retry-After`-тэй буцаана. Клиент түүнийг
хүндэтгэж дахин оролдоно — **өдрийн зарлагын хязгаараас бусад тохиолдолд**:
тэр нь ажлын наслалтын дотор арилахгүй тул дахин оролдох нь зөвхөн worker-ийн
слот иднэ.
